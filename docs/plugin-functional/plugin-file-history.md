# `plugin-file-history` · Lore 文件历史与版本管理

**状态：现有基础快照；目标迁移到 Lore 版本操作。** 全栈插件：Rust 后端通过受控 Lore 适配层管理版本，前端贡献 `detail-tab:history`。LoreGUI 是 Lore 的桌面客户端，不直接嵌入其完整 GUI；参考其可与 GUI 分离的 `lore-vm`/Lore 核心能力，历史面板继续使用本应用的 Mantine 界面。版本记录的缩略图与展示属性由独立的 `plugin-history-metadata` 负责。

## 职责与边界

- 管理用户明确纳入 Lore 仓库范围的 Lore 版本操作：查询版本历史、工作区状态、版本内容/差异，以及经过确认的恢复。
- Lore 是版本内容、提交和分支的事实来源；本插件不再把 `db.history.*` 快照表当作版本真相，也不自行复制文件正文来构造第二套版本库。
- 本插件拥有 Lore 操作编排和时间线骨架；`plugin-history-metadata` 独占版本展示元数据、缩略图副本和元数据卡片。Lore 适配服务拥有仓库连接、revision 查询与写入。前端不直接访问 Lore 数据目录、SQLite 或命令行。
- 仓库范围必须由用户选择或确认。仅对仓库根目录内、且符合忽略/大小策略的路径启用版本管理；不得因收到普通 `file:changed` 事件就把任意磁盘路径自动加入仓库。
- 默认使用用户选择的本地 Lore 仓库。远端服务仅在用户主动配置连接后使用。仓库/服务初始化、存储位置、同步策略和凭据属于设置流程，不在历史面板里隐式完成。

## 功能与显示

- `focusRef.kind === "file"` 且路径位于受管理仓库内时显示该文件的版本时间线；目录、仓库外路径和未初始化仓库显示相应引导。焦点变化后不得残留上一文件的记录。
- 时间线按版本时间倒序分页展示 revision ID、提交说明、作者（若仓库提供）、时间和来源分支；通过 `history-record:metadata` 子插槽挂载 `plugin-history-metadata` 提供的缩略图、大小、类型与尺寸。支持刷新、加载更多、空态、离线/未连接和错误重试。
- 当前工作区有未提交改动时，显示“有未保存版本”状态，并提供查看变更和创建版本入口。文件系统变化只更新 Lore 工作区状态，不直接产生提交；避免 watcher 对每次写入都制造不可解释的版本。若以后增加自动检查点，必须作为显式可配置策略单独定义频率、合并规则和排除项。
- 用户选择两个版本后可比较差异。文本内容使用行级差异视图；二进制文件显示版本差异摘要，并从 `plugin-history-metadata` 取得该版本的展示属性，不尝试文本解码。过大或无权限读取时解释限制并允许重试。
- “查看版本”是只读操作，不改当前文件；“恢复此版本”是写入操作，必须展示目标路径、所选版本及覆盖影响，在用户确认后执行。若当前文件存在未提交改动，先提供保留当前改动/取消选项，不得静默覆盖。
- 恢复通过读取所选 Lore 版本并写回目标文件，再将恢复结果作为新的工作区变化/版本记录；不得通过把分支头倒退或无提示执行破坏性 reset 来模拟恢复。失败时保留当前磁盘内容并给出可恢复错误。
- 新版本进入时间线使用轻量淡入；加载更多、差异切换和恢复状态切换遵守全局动效约定。提交/恢复期间显示进度并防止重复触发；用户取消后清除本次任务状态。

## 交互与状态

- 核心状态：`unconfigured`（仓库未配置）、`outside-repository`、`loading`、`clean`、`dirty`、`staging`、`committing`、`loading-diff`、`restoring`、`offline`、`error`、`cancelled`。
- 状态只属于当前焦点文件和仓库会话。请求带 `path + repositoryId + requestToken`；焦点、分支或仓库切换时取消/丢弃迟到响应。
- 创建版本需要用户确认版本说明；提交成功后接收 Lore 返回的 revision ID，再刷新文件历史与工作区状态。提交失败保留 dirty 状态和输入说明，提供重试。
- 版本切换分为“选择版本查看”和“恢复版本”两种明确动作。查看只切换历史内容/差异区；恢复需要二次确认，完成后仍留在该文件并刷新时间线。
- 对历史 revision 行通过 `host.contextMenu.registerItem` 注册“查看差异”“切换到此版本”等动作；动作 descriptor 归 file-history 所有，恢复仍执行本插件已有的 dirty 检查/确认/Lore 调用。历史信息插件只负责显示元数据并可发出恢复请求。
- 禁用插件或关闭窗口时取消查询、差异读取和恢复任务；正在进行的不可中断存储事务由后端报告最终结果，不能向 UI 伪报取消成功。

## 数据处理与存储

- 后端从文件监听/操作事件接收变更提示后，向 Lore 查询仓库状态；事件仅用于失效与刷新，不包含或传递文件正文。重复事件按 repository/path 合并，避免无意义刷新。
- 版本列表、文件历史、指定 revision 内容、差异与工作区状态均由 Lore 适配层提供。大文件内容按 Lore 支持的块/流式接口读取，UI 仅请求当前页面或差异所需数据，并可取消。
- 本地 Lore 仓库保存版本内容和版本元数据；本插件偏好只存仓库选择、历史分页/显示偏好和用户选择的自动策略（初始默认关闭）。凭据由安全凭据存储管理，不进入 localStorage、插件事件或普通配置文件。
- 原 `db.history.*` 记录只含旧快照元信息时，保留为只读的“旧记录”/迁移来源说明，不伪装成可恢复的 Lore 版本；不得在未验证可恢复性前自动删除。若旧实现确有快照正文，迁移须逐项验证内容哈希与路径映射，成功后才标记迁移完成。
- Lore 仓库生命周期（初始化、连接、备份/同步、断开、删除）由用户可见的设置/仓库管理流程拥有。删除仓库或清理版本必须明确影响范围并二次确认；删除插件不得删除用户仓库。
- 插件卸载、Lore 暂不可用或仓库离线时保留仓库数据；已有文件浏览/打开不因历史服务不可用而阻塞。

## 插件交流与能力契约

目标链路：文件系统通知 → `file:changed` 失效提示 → `plugin-file-history-backend` 查询 Lore 工作区 → `history:updated {repositoryId,path}` → 前端按当前焦点刷新；用户版本操作 → history backend → Lore adapter → 返回 revision/task 状态 → 前端更新。

- 计划新增受权限控制的 `lore.repository.*`、`lore.workspace.status`、`lore.file.history`、`lore.file.readRevision`、`lore.diff`、`lore.change.stage/commit`、`lore.file.restore` 等能力；命名与请求/响应字段须在 Rust contracts、宿主能力注册、插件 manifest 和 TS SDK 中统一冻结后才能实现。
- 跨插件只传不透明 `repositoryId`、文件 `Ref`、revision ID 和任务 ID；禁止传整个仓库对象、正文或本地凭据。详情插件只提供焦点/插槽，文件浏览器只提供路径焦点，均不直接调用 Lore。
- UI 通过 `detail-tab:history` 展示；版本行的元数据卡片由 `plugin-history-metadata` 贡献到 `history-record:metadata` 子插槽。历史更新事件仅做失效通知，前端按需重新查询，不把版本正文或缩略图 bytes 放入全局事件总线。
- 核心后端操作通过 Rust Lore 绑定/适配层调用，不由前端启动 CLI。若上游能力必须依赖 `loreserver`，需在 P6-69 验证本地服务打包、生命周期和健康状态；这会触及 D4 的“单进程、无 sidecar”决策，必须一并评估架构代价。远端服务连接必须显式配置。

## 失败处理与验收

- 覆盖未配置仓库、仓库外文件、只读/权限拒绝、仓库离线、Lore 服务不可用、版本不存在、历史分页、文本与二进制 diff、大文件取消、未提交改动下恢复、恢复失败、重复 watcher、旧记录保留、插件卸载清理。
- 验收要求：仓库内变更只标记 dirty，不自动生成提交；用户创建版本后可查询并查看旧内容；查看旧版本不改变磁盘文件；恢复必须确认、不会回退分支历史且恢复结果可再次追踪；仓库外路径永不被静默纳管；Lore 故障不影响普通浏览。
- 依赖风险：Lore/LoreGUI 当前为 pre-1.0 上游，API 与磁盘格式可能变化。正式实现前固定兼容版本/revision，核查许可证、数据格式迁移、Windows 打包和服务启动方式；以 Lore 核心能力为版本数据模型，以 LoreGUI 的 `lore-vm` 解耦设计为复用参考，不把桌面 GUI 当作嵌入组件。
